## 2. The three shipped facts this record stands on

Measured at `5396fb6`.

**(a) `resolve_url()` returns the clean surface, by construction.** It resolves
each `(reference, base)` pair to a raw absolute string, hands the whole vector to
the shared parser, and returns that parse's `clean_url` column
(`R/resolve.R:235-245`, `out <- parsed$clean_url` at `:245`). Surface (c) is
therefore its public return today, exactly as `output-contracts.md:161` records.

**(b) The resolved absolute string already exists before cleaning, and the
standard serializer already accepts a raw string.** `.resolve_one_raw()`
(`R/resolve.R:139-158`) returns the RFC 3986 §5.3 recomposition — an absolute
URL string — and `resolve_url()` collects it into `resolved_raw`
(`R/resolve.R:235-239`) one step *before* the parse that produces `clean_url`.
`serialize_url()`'s first formal is a character vector of URLs
(`R/serialize.R:408`, `:444-447`). So routing the resolved string to surface (b)
is a hand-off between two shipped functions, not new serialization machinery.

**(c) The merge claims to be standard-agnostic.** `R/resolve.R:3-7` states the
file "adds NO new per-standard divergent behavior of its own (PRD v2 D6): the
base-merge (section 5.2.2) is identical under both standards", and the exported
documentation repeats it (`R/resolve.R:162-171`). Its authority is PRD v2 D6
(`design/prd/url-standard-selector-v2.md:106`), whose rationale reads:
"Decomposing the WHATWG base-URL algorithm against RFC 3986 §5.3 shows no
genuinely new divergent behavior once the axes above exist — only a shared merge
step plus composition of already-scoped axes."

## 3. The decision

### D-A. `resolve_url()`'s default output does not change; a standard surface is added opt-in

`resolve_url()` keeps returning the clean `clean_url` string (surface c) by
default, byte-for-byte. It gains **one** new argument that routes the resolved
absolute string to `serialize_url()` instead:

```r
resolve_url(relative_or_absolute, base_url, url_standard = NULL,
            output = c("clean", "serialized"), form = c("source", "normalized"),
            ...)
```

- `output = "clean"` (default) — today's behavior and today's bytes: parse the
  resolved string and return `clean_url` (`R/resolve.R:244-245`).
- `output = "serialized"` — return `serialize_url(<resolved absolute string>,
  standard = url_standard, form = form)`, i.e. surface (b): full string,
  fragment preserved, credentials reconstructed (`R/serialize.R:351-354`).
  It **requires an explicit `url_standard`**; `url_standard = NULL` with
  `output = "serialized"` is an error, because `NULL` selects no standard and
  there is nothing to serialize *to*. This is also what keeps D-C true.
- `form` is passed through to `serialize_url()` and is meaningful only for
  `url_standard = "rfc3986"`, matching that function's own contract
  (`R/serialize.R:409-413`).

**Why the default does not move.** P2.2 §1 SETTLED that clean output (surface c)
and standard serialization (surface b) are **distinct surfaces with different
contracts** — (c) omits the fragment and never reconstructs credentials and is
"intentionally lossy" (`P2.2 §1c`), (b) is fragment- and credential-complete and
spec-exact (`P2.2 §1b`) — and its invariant 1 forbids one standing in for the
other (`P2.2 §5(1)`). Making `resolve_url()` return (b) by default would not be a
better default; it would be surface (c)'s named accessor silently emitting
surface (b), which is the substitution that record forbids. The gap
`RURL-fupsemxr` reports is **availability** — there is no way to ask for the
resolved URL serialized per the standard — not a wrong default. An added
argument closes an availability gap without contradicting an accepted record.

**Spelling.** `output = c("clean", "serialized")` is a **choice**. It would
change if the owner prefers the surface letters themselves, or a separate
`resolve_url_serialized()` entry point; what it must not become is a value that
makes the default anything other than today's clean string.

### D-B. The reference-resolution merge becomes standard-aware; this supersedes PRD v2 D6's *rationale*

The merge is **not** identical under both standards. `R/resolve.R:3-7` and
`design/prd/url-standard-selector-v2.md:106` are wrong on this point, and the
falsification is measurement, not argument: of **274** base-null-excluded
WPT base-relative success rows, **212** are exact and **62 differ** — by base
scheme, `file` 30, `http` 27, non-spec 5; **16** of the 62 rurl rejects outright.
(Provenance and re-derivation duty: §4.)

Three rule families account for the non-`file:` differences. Each is a rule
WHATWG applies while parsing the **reference**, which rurl either applies later
(to the already-merged absolute string) or not at all:

1. **Same-special-scheme references are relative.** A reference whose scheme
   equals the base's special scheme is RELATIVE under WHATWG's "special relative
   or authority" state, not absolute. `http:foo.com` against base
   `http://example.org/foo/bar` resolves to `http://example.org/foo/foo.com`;
   rurl gives `http://foo.com/`, because `.split_uri_ref()` sees a scheme and
   takes RFC 3986 §5.2.2's first branch — "absolute reference: base is
   irrelevant" (`R/resolve.R:143-148`).
2. **Backslash is a slash *during reference parsing*, not only downstream.**
   rurl recognizes literal backslash for special schemes, but the recognizer runs
   in the parser that consumes the *merged* string, so the merge itself treats
   `\` as an ordinary path byte. Reference `\x` against the same base resolves to
   `http://example.org/x` under WHATWG; rurl merges it as a relative path segment
   and the downstream recognizer then rewrites the result, giving
   `http://example.org/foo//x`.
3. **Leading/trailing C0-or-space is stripped from the reference.** Reference
   `` foo.com `` (leading space, trailing spaces) resolves to
   `http://example.org/foo/foo.com`; rurl currently percent-encodes the leading
   space into the path.

**Therefore:** under `url_standard = "whatwg"`, reference resolution applies the
WHATWG reference-parsing rules **before** the merge. Under
`url_standard = "rfc3986"` it stays RFC 3986 §5.2–§5.3 exactly as today. The
standard-agnostic claim at `R/resolve.R:3-7` and `:162-171` is retired with the
implementation; the file comment must not survive the change that falsifies it.

**Supersession, stated precisely.** This supersedes **D6's rationale**, not the
whole of D6. D6's *conclusions* stand: `resolve_url()` is a public entry point
(shipped, `R/resolve.R:213-249`), `url_standard` flows through to the path, host,
backslash and port axes, and the merge composes already-scoped axes. What is
superseded is the sentence claiming the decomposition "shows no genuinely new
divergent behavior once the axes above exist". It held **only for the axes D6
enumerated** — path, host, backslash, port — and the three families above are
none of them: they are *reference-parsing* rules, a stage D6's decomposition did
not separate from the merge. `supersedes: []` in the frontmatter is correct as
written, because PRD v2 is not a P-tier record and this record removes no
conclusion of it.

### D-C. The `url_standard = NULL` path stays byte-frozen

Nothing in D-A or D-B touches `url_standard = NULL`. ADR 0007 freezes the NULL
selector: "**No default flip.** `url_standard = NULL` remains byte-for-byte
compatible" (`design/adr/0007-url-standard-selector.md:46`). Concretely,
`tests/testthat/test-resolve-url.R:150-152` pins

```r
resolve_url("g\\h", "http://a/b/c/")  # -> "http://a/b/c/g\\h"
```

verbatim, and that expectation **must not move**. D-B's reference-parsing rules
are selected by `url_standard = "whatwg"` and are unreachable at `NULL`; D-A's
`output = "serialized"` is an error at `NULL` for the same reason. A diff that
changes any `url_standard = NULL` resolve output is a defect in this decision's
implementation, not a consequence of it.

### D-D. `format_url()` is in scope for the 3.0 line, with this matrix

`format_url()` ships in 3.0. S3-F3's complaint is that the protocol "names safe
decoding, structural delimiters, invalid UTF-8, controls, bidi controls, and
invisible characters, but gives no required output for any of them"; what follows
is a required output for each, minimal enough to implement and test.

**The cap that makes this cheap.** `output-contracts.md:209` already SETTLED that
surface (d) is **not reparsable** — "never re-enters serialization" — and carries
no round-trip and no identity guarantee. `format_url()` therefore does **not**
have to emit a URL. That is what buys the escape tokens and the trailing
annotation block below; without the cap, every one of them would be a round-trip
violation.

**Two token spellings, and one rule that makes them unambiguous.**

| token | meaning |
|---|---|
| `<redacted>` | the entire userinfo slice, whatever it contained |
| `<U+XXXX>` | one escaped code point, `U+` notation, uppercase hex, ≥4 digits (e.g. `<U+202E>`, `<U+0000>`, `<U+10FFFF>`) |

The rule: **`format_url()` never emits `<` or `>` that came from data.** `%3C`
and `%3E` are left percent-encoded in every component (rule E1 below), and a
literal `<`/`>` reaching the formatter is emitted as `<U+003C>` / `<U+003E>`.
Consequently every `<…>` in the output was written by the formatter. This is why
the userinfo token cannot be mistaken for a real credential: a conformant
credential cannot contain a bare `<` or `>` — WHATWG's userinfo percent-encode
set is a superset of the query set, which encodes `<` and `>`, and RFC 3986's
`userinfo` production admits neither — and even a non-conformant one is escaped
by E1 rather than passed through. The token is emitted **in place of** the
component and is never derived from it, so it is fixed-width regardless of input
and leaks neither the password's presence nor any length.

**Escape rules.**

| # | rule |
|---|---|
| E1 | `<` and `>` are never emitted from data: `%3C`/`%3E` stay percent-encoded; a literal one is escaped as `<U+003C>` / `<U+003E>` |
| E2a | **immutable blocks**, enumerated as ranges: U+0000–U+001F and U+007F–U+009F (the C0/C1 controls, covering NUL and LF), U+D800–U+DFFF (surrogates — see E3), and the three Private_Use ranges U+E000–U+F8FF, U+F0000–U+FFFFD, U+100000–U+10FFFD. Every code point in them is emitted as `<U+XXXX>` |
| E2b | **the hazard list**, a closed enumeration rurl owns: U+00AD, U+061C, U+180E, U+200B–U+200F, U+202A–U+202E, U+2060–U+2064, U+2066–U+206F, U+FEFF, U+FFF9–U+FFFB. Every code point in it is emitted as `<U+XXXX>`. This **must** include, and does include, the bidi formatting characters U+202A–U+202E (LRE, RLE, PDF, LRO, RLO) and U+2066–U+2069 (LRI, RLI, FSI, PDI), plus U+200E/U+200F, U+061C, U+200B–U+200D, U+00AD and U+FEFF |
| E2c | **nothing else is escaped for being a character.** No code point outside E1, E2a and E2b is escaped, whatever general category the installed Unicode data assigns it. In particular an **unassigned** code point is not escaped unless it falls in an E2a range; it passes through E5 as an ordinary character |
| E3 | bytes that are not valid UTF-8, and percent-triplets that do not decode to valid UTF-8, are **not** decoded; they are emitted as uppercase `%XX` (this is S3-F3's `%FF`). **E3 owns lone surrogates.** A lone surrogate cannot occur in valid UTF-8, so it can only reach the formatter as invalid bytes, which E3 leaves as `%XX` — E2a's U+D800–U+DFFF range is the belt-and-braces case of a surrogate arriving already as a code point (an R string built from a `\uD800` escape). The two cannot both fire: E3 acts on undecoded bytes, E2 on decoded code points |
| E4 | decoding never fabricates structure: within a component, a percent-triplet whose decoded character is a delimiter of that component or of the URL grammar — `/ ? # @ : [ ] % \`, plus `& = +` inside a query — stays percent-encoded (this is S3-F3's `/a%2Fb` and `?x=a%26b%3Dc`) |
| E5 | everything else decodes to its character, so `%C3%A9` displays as `é`. This is the surface's entire purpose and the only place decoding happens |

**Why E2 is three enumerations and not five general categories.** The obvious
spelling — "escape general category `Cc`, `Cf`, `Cs`, `Co`, `Cn`" — makes
`format_url()` output a function of the **Unicode data version** rather than of
the URL: `Cn` (unassigned) shrinks with every Unicode release and `Cf` grows to
match, so the same URL would format differently after a dependency bump, with no
code change and no diff to notice it. That is precisely the class of variance
`RURL-gxqdmpcp` spent an epic removing from rurl's output, and the drift vector
is live rather than hypothetical: `DESCRIPTION:44` pins `punycoder (>= 1.2.0)` —
a lower bound, not a Unicode-version pin — while the installed build measured at
`5396fb6` is `punycoder 1.2.1.9000` and `punycoder::unicode_versions()` reports
`"16.0.0" "17.0.0"`, i.e. the Unicode data under rurl is already multi-valued.
So **E2 performs no runtime general-category lookup at all**: E2a's ranges are
immutable under the Unicode Stability Policy (`Cc`, `Cs` and `Co` membership can
never change), and E2b is a list this package owns, so extending hazard coverage
for a future Unicode release is a deliberate code change carrying a NEWS entry
and a fixture diff — a reviewable event, which a silent data bump is not. Do not
"simplify" E2 back to five category names.

**Component matrix.**

| component | rendered as | decoded? |
|---|---|---|
| scheme | as parsed | n/a |
| userinfo | `<redacted>@`, emitted **iff** any userinfo was present (including a bare `@`); never split into user/password | never — the bytes are discarded, not transformed |
| host | the Unicode (IDNA) spelling, then E2a/E2b applied | n/a; see the host rule below |
| port | as parsed, verbatim; **no** default-port elision (elision is normalization — surface b) | n/a |
| path | E1–E5 | per E3/E4/E5 |
| query | E1–E5, with `& = +` added to E4's delimiter set | per E3/E4/E5 |
| fragment | E1–E5, and **shown** | per E3/E4/E5 |
| annotation block | see below | n/a |

**Host — both spellings, always visible when they differ.** The host is rendered
in its Unicode form; when the ASCII/A-label (punycode) form differs, the output
appends `[host: <ascii-form>]` to the annotation block. When the two are equal —
every plain-ASCII host — nothing is appended. S3-F3's own example therefore
displays as:

```
https://münchen.de/p  [host: xn--mnchen-3ya.de]
```

A homograph is thus never invisible: the reader always sees the A-label whenever
it is not simply the host they already read.

**Output shape.** `scheme://[<redacted>@]host[:port]path[?query][#fragment]`,
followed — when any annotation applies — by two spaces and the annotation block.
A row that did not parse formats as `NA`, matching the accessors. The result is
**not a URL**, is never fed to serialization, mutation baselines or keys
(`P2.2 §5(1)`; `output-contracts.md:209`), and the documentation must say so at
the top of the page.

**`format_url()` takes no cleaning or presentation dials.** Not
`path_encoding`, not `host_encoding`, not the query dials. Its escape matrix
**is** its presentation rule, and accepting `path_encoding = "decode"` would
hand a caller back the exact `/a%2Fb` → `/a/b` hazard E4 exists to prevent
(S3-F3 records that shipped `path_encoding = "decode"` behavior; its own
`R/parse-phases.R` line citation is dated to S3's baseline and has since moved,
so it is named here by dial, not by line). `format_url()` takes the parse
options it needs to parse, and nothing else — the same no-dials posture
`serialize_url()` already holds (`R/serialize.R:370-373`).

**What is chosen, not derived.** Three spellings here have no anchor and are
choices:

1. the `<…>` token bracket — it would change if the output must be pasteable
   into HTML or a shell without further escaping, or if the owner prefers a
   structured (data-frame) return over one string;
2. showing that credentials were **present** at all — it would change if the
   owner rules that presence is itself the leak, in which case the token is
   dropped entirely rather than made ambiguous;
3. the trailing annotation block rather than an inline parenthesis — it would
   change if display output must remain a single URL-shaped token, which
   `output-contracts.md:209` currently says it need not be.

### D-E. The resolver verdict surface is deliberately NOT shipped in 3.0

VAL-O3 closes as **not shipped, with a reason recorded** — not as silence, which
is the failure mode the cell exists to prevent.

P2.3 §3 (`decisions/P2.3-validation-verdicts-migration.md:185-206`) settles the
*layering*: three independent objects — base-URL verdict, reference verdict,
merged-output verdict — each carrying L1/L2. Two of the three need no new
surface, and the third cannot be built from what is accepted:

- **base-URL verdict** — already reachable: `get_parse_verdicts()` is exported
  (`NAMESPACE:17`; `R/verdicts.R:315`) and the base *is* a full URL.
- **merged-output verdict** — already reachable **once D-A lands**, by calling
  `get_parse_verdicts()` on the resolved absolute string that
  `output = "serialized"` makes available. P2.3 defines this verdict as exactly
  "L1/L2 of the resolved absolute URL … then re-parse", which is that call.
- **reference verdict** — **not** reachable, and not specifiable here. A relative
  reference has no standalone parse frame. Measured at `5396fb6`:
  `get_parse_verdicts("../h")` returns `layer1_syntax_verdict = "fail"`,
  `layer2_policy_verdict = "admitted"`, `layer3_annotation_state =
  "not-applicable"`. That is the verdict of reading a reference as though it were
  a URL — it is not the "reference verdict" P2.3 means, since `../h` is a
  perfectly well-formed relative reference. Producing the intended value needs a
  verdict model over RFC 3986 §4.2 relative references (which layers apply, what
  `admitted` means for a fragment that has no scheme to admit), and **no accepted
  record defines one**.

Shipping a two-thirds companion would be worse than shipping none: it would put
the exported name `get_resolve_verdicts()` on an object whose middle layer is
either absent or quietly wrong. So: **no resolver verdict companion in 3.0.**
`resolve_url()` keeps its `NA`-on-failure signal, which P2.3 already SETTLED as
an L1-fatal projection preserved for back-compat
(`validation-intervention-contract.md:247`). Reopening this requires a new
record defining the relative-reference verdict model first; it is a
specification gap, not a scheduling one, and it is written down here so the next
reader finds the reason rather than the silence.

## 5. Non-scope

- **No host, IDNA, IP-literal or PSL semantics.** D-D renders the host in two
  spellings; which spelling *is* the host is G3.H's (RCON-08).
- **No cleaning dial.** The 25 dials, their order and lossiness stay G3.8's
  (`P2.2 §5.3`). D-A changes no clean output; D-D consumes none of them.
- **No comparison key.** Surface (e) is P3.1 / G3.K's. Neither the display string
  nor the serialized resolve output may be keyed on.
