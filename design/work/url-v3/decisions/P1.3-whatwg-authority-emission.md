# P1.3 — WHATWG `//` emission follows the parsed host

## Decision (PROPOSED)

> This record is the agent's **proposed** disposition, offered for the owner to
> ratify, reject, or adjust. Nothing here is binding until the owner merges it
> (P0.1 §4).

## 1. The defect

Scored against the full imported web-platform-tests suite
(`inst/bench/wpt-url-cases.json`, 336 success rows) using upstream's own `href`
as the oracle, `serialize_url(standard = "whatwg")` reproduced 326 of 336
exactly. All ten differences were one family in one scheme:

| input | WHATWG `href` | rurl (before) |
|---|---|---|
| `file:C\|/m/` | `file:///C:/m/` | `file:/C:/m/` |
| `file:C\|\|/m/` | `file:///C\|\|/m/` | `file:/C\|\|/m/` |
| `file:/example.com/` | `file:///example.com/` | `file:/example.com/` |
| `file:.` | `file:///` | `file:/` |
| `file:/C\|/` | `file:///C:/` | `file:/C:/` |
| `file:` | `file:///` | `file:/` |
| `file:?q=v` | `file:///?q=v` | `file:/?q=v` |
| `file:#frag` | `file:///#frag` | `file:/#frag` |
| `file:.//p` | `file:////p` | `file:/.//p` |
| `file:/.//p` | `file:////p` | `file:/.//p` |

Every hard part was already right — the `C|` → `C:` drive-letter
normalization, the `C||` non-normalization, dot-segment removal. The only delta
was the authority introducer.

## 2. Root cause: the `file:` host state, not the serializer

WHATWG's **file state** sets url's host to the **empty string** before any
authority is read, and nothing in the file host state can put it back to null
(`localhost` is explicitly *mapped to* the empty string, not dropped). So every
`file:` URL has a **non-null** host, and `#concept-url-serializer` step 2 — "if
url's host is non-null, append `//`" — always fires for `file:`.

rurl's WHATWG `file:` parser (`.parse_whatwg_file_urls_vec()`) recorded
`NA` for the host-less forms, so `host_kind` read `absent`, and the serializer
rendered that record faithfully. A parse-model gap, not a rendering bug — and
under the standing precedent (P5.4 §6) it is filed against the parser and not
compensated for downstream.

## 3. Why this reopens P1.2 D-C

P1.2 D-C reads:

> The standard serializers must emit `//` **if and only if**
> `authority_delimiter_present` is `TRUE`, and must **not** re-derive `//` from
> `host_kind`. […] which cannot distinguish a delimiter-present empty-authority
> input from a delimiter-absent one.

The italicized premise **was the defect**. Measured at `608334e` over the 336
WPT success rows, `host_kind != "absent"` and `authority_delimiter_present`
disagreed on exactly **26** rows — and all 26 were `file:` rows whose
empty host the parser had recorded as null. With the `file:` host model
repaired, the two facts agree on **326** of the 336 rows and disagree on
exactly the **10** rows in §1, where the standard sides with the host.

So D-C's rule and D-C's own justification now point in opposite directions.
D-C was written to stop the serializer *losing* a distinction; keeping it would
now make the serializer *emit the wrong string* on the standard's own suite.

## 4. The decision

**D-A. The WHATWG serializers emit `//` if and only if the URL's host is
non-null** — `host_kind != "absent"` — which is `#concept-url-serializer`'s own
condition and nothing else. `authority_delimiter_present` is **not** consulted
by them. The single predicate lives in `.whatwg_authority_emitted()` so both
WHATWG serializers (the clean surface and the full-string serializer) cannot
drift apart, and both take `authority_delimiter_present` in their signature and
`force()` it, marking it deliberately unconsumed.

**D-B. The RFC serializers keep P1.2 D-C unchanged.** Under the
source-preserving posture the `//` in the *input* is precisely the fact being
rendered: `file:/example.com/` genuinely carries no authority under RFC 3986,
and its `rfc3986` serialization is unchanged in both forms.
`authority_delimiter_present` therefore stays canonical state, stays in the
record, and stays load-bearing — it is narrowed to one consumer, not retired.

**D-C. A WHATWG `file:` URL's host is never null.** The empty string is the
host-less spelling, `localhost` maps to it, and `NA` is reserved for "this row
did not parse". This is a `file:`-scheme parse rule under
`url_standard = "whatwg"` only; it makes no claim about any other scheme and
none at all under `rfc3986`.

**D-D. The public `host` column is NOT widened.** `.assemble_parse_result_vec()`
still maps an empty host to `NA`, so `get_host("file:/example.com/")` reports
`NA`. That collapse is a **general accessor rule** — `foo:///bar` reports `NA`
too — and predates this defect. Making the public column three-valued is a
separate surface decision on the P1.1 presence axis and is deliberately **not**
taken here. The empty-vs-absent distinction lives where P1.1/P1.2 D-B put it:
in `host_kind`.

## 5. Evidence

At `608334e` + this slice, measured not transcribed:

| Claim | Before | After |
|---|---|---|
| WPT success rows serializing to upstream `href` (`whatwg`) | 326 / 336 | **336 / 336** |
| WPT must-fail rows rejected (`whatwg`, both forms) | 202 / 202 | 202 / 202 |
| Rows accepted, `whatwg`, 1460-input probe corpus | 859 | **859** |
| Rows accepted, `rfc3986`, same corpus | 1045 | **1045** |
| `rfc3986` serializations changed (`source` + `normalized`) | — | **0** |
| Public parse frame changed (`parse_status`/`host`/`path`/`clean_url`/`domain`/`port`, 4 profiles) | — | **0** |
| WHATWG serializations changed | — | 276, **all** `file:` |

The 276 changed rows are the `//` insertion and nothing else: 272 are exactly
`sub("^file:", "file://", before)`, and the remaining 4 are the `file:.//p` /
`file:/.//p` family, where a non-null host correctly retires the `/.` guard and
yields the standard's `file:////p`.

The probe corpus is the 538 WPT inputs (success + failure), three 256-row
host-octet sweeps, and a hand-built `file:`-shape set; it is regenerated by
script rather than committed, because its role is a before/after invariance
comparison, not an oracle (P5.3 CLAIM-1).

**Acceptance invariance is the load-bearing check here**, per the precedent set
by RURL-savatsuc: in this parser a change to what the host model admits can
silently widen *acceptance* rather than only serialization. It did not: 859 and
1045 accepted, before and after, and 202/202 must-fail rows still rejected.
